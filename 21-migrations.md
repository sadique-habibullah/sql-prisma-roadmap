# 21. Migrations

**Goal:** Evolve the database schema over time with Prisma Migrate, understand how it coexists with Supabase's own tooling, and establish a single source-of-truth strategy.
**Prerequisites:** [01 — Setup & Environment](./01-setup-and-environment.md), [04 — Tables & Models](./04-tables-and-models.md)

## Comparison Table

| Concept | SQL (PostgreSQL) | Prisma |
|---|---|---|
| Add a column | `ALTER TABLE users ADD COLUMN bio TEXT;` | Add `bio String?` to model + `prisma migrate dev` |
| Remove a column | `ALTER TABLE users DROP COLUMN bio;` | Remove field from model + `prisma migrate dev` |
| Rename a column | `ALTER TABLE users RENAME COLUMN old TO new;` | Add `@map("old")` on renamed field OR write custom migration SQL |
| Change a column type | `ALTER TABLE users ALTER COLUMN age TYPE BIGINT;` | Change Prisma type + `prisma migrate dev` (may fail if data is incompatible) |
| Create migration file | Write `.sql` file manually | `prisma migrate dev --name describe-the-change` |
| Apply pending migrations | `\i migration.sql` or `psql < file.sql` | `prisma migrate deploy` |
| Check migration status | `SELECT * FROM _prisma_migrations;` | `prisma migrate status` |
| Rollback a migration | Write a reversal `.sql` file | No built-in rollback — write a new forward migration |
| Reset database (dev only) | `DROP SCHEMA public CASCADE; CREATE SCHEMA public;` | `prisma migrate reset` (dev only — DESTRUCTIVE) |
| Introspect existing DB | Inspect `information_schema` manually | `prisma db pull` generates schema from existing tables |
| Apply schema without migration | N/A | `prisma db push` (dev prototype only — not tracked) |
| Supabase dashboard change | Creates schema drift | Run `prisma db pull` to sync, then `prisma migrate dev` to generate a new migration |

### Code: Migration workflow

```bash
# 1. Edit prisma/schema.prisma (add a field, model, etc.)

# 2. Generate and apply a migration (uses DIRECT_URL, port 5432)
npx prisma migrate dev --name add-bio-to-users
# Creates: prisma/migrations/20240101000000_add_bio_to_users/migration.sql
# Applies: runs the SQL against your database
# Regenerates: prisma generate (rebuilds the client)

# 3. In production/CI: apply existing migrations
npx prisma migrate deploy

# 4. Check status
npx prisma migrate status
```

### Code: What the generated migration looks like

```sql
-- prisma/migrations/20240101000000_add_bio_to_users/migration.sql
-- This file is auto-generated by Prisma Migrate.
-- You can edit it before applying, but be careful.

ALTER TABLE "users" ADD COLUMN "bio" TEXT;
```

### Code: Adding a custom CHECK constraint in a migration

```sql
-- Edit the generated migration file to add unsupported DDL:
ALTER TABLE "users" ADD COLUMN "age" INTEGER;

-- Add a CHECK constraint that Prisma can't generate:
ALTER TABLE "users" ADD CONSTRAINT "users_age_check" CHECK (age >= 0);
```

### Code: Handling Supabase dashboard changes (drift)

```bash
# Scenario: someone added a column via the Supabase SQL editor

# Step 1: sync the schema from the database
npx prisma db pull
# This updates schema.prisma to match the actual database

# Step 2: create a migration that reflects the change
npx prisma migrate dev --name sync-supabase-dashboard-change
# Prisma detects that the DB already has the column
# and generates a migration file that matches what exists

# Step 3: commit both schema.prisma and the migration file
```

### Code: `datasource` with both URLs (migration reminder)

```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")   // port 6543 — runtime queries
  directUrl = env("DIRECT_URL")     // port 5432 — migrations ONLY
}
```

### Code: Keeping `auth`/`storage` schemas out of Prisma

```prisma
datasource db {
  provider  = "postgresql"
  url       = env("DATABASE_URL")
  directUrl = env("DIRECT_URL")
  schemas   = ["public"]           // ONLY manage "public" — never "auth", "storage", etc.
}
```

## What's Really Happening

**`migrate dev` vs `migrate deploy`:**
- `migrate dev` — for development. Creates a new migration file, applies it to your dev database, and regenerates the Prisma Client. Use it on your local machine.
- `migrate deploy` — for production/CI. Applies all pending migration files in order. Does NOT create new ones. This is what your deploy pipeline should run before starting the application.

**Why `DIRECT_URL` is required for migrations** — `prisma migrate dev` and `prisma migrate deploy` use a separate connection to apply DDL statements (`CREATE TABLE`, `ALTER TABLE`, etc.). Supabase's Supavisor pooler in transaction mode cannot handle DDL in a pooled context. `DIRECT_URL` (port 5432) bypasses the pooler and connects directly to Postgres. Without `directUrl`, migrations will fail with obscure errors.

**Single source of truth — the recommendation** — there are two common approaches when using Prisma + Supabase:

| Approach | Prisma as source | Supabase dashboard as source |
|---|---|---|
| Schema changes | Edit `schema.prisma`, run `migrate dev` | Edit in Supabase SQL editor, then `db pull` |
| Migration files | Tracked in git, deterministic | Not tracked, hard to reproduce |
| Recommended for | Most teams building a product | Rapid prototyping only |

**Our recommendation: use Prisma as the single source of truth.** All schema changes go through `schema.prisma` + `migrate dev`. Never add columns or tables via the Supabase dashboard in production. This keeps migrations deterministic, version-controlled, and reproducible.

**`prisma db push`** — skips migration files entirely and directly syncs your schema to the database. Fast for prototyping, but the changes aren't tracked. Never use `db push` in production or shared environments.

**Supabase-managed schemas** — Supabase owns `auth`, `storage`, `realtime`, `extensions`, and `supabase_functions`. Do not add these to `datasource.schemas`. Prisma will not manage them, and you won't accidentally create conflicting migrations.

> **Leaky abstraction alert:** Prisma cannot roll back migrations. If a migration causes a problem in production, the fix is a new forward migration. Keep individual migrations small and focused — large migrations that do many things at once are hard to debug and even harder to recover from.

## Practice

1. Add a `bio String?` field to the `User` model. Run `prisma migrate dev --name add-user-bio`. Open the generated SQL file in `prisma/migrations/` and read it. Does it match what you expected?

2. Simulate a Supabase dashboard change: run `ALTER TABLE users ADD COLUMN phone TEXT` directly in SQL. Then run `prisma db pull` and `prisma migrate dev`. What does Prisma do with the drift?

3. What is the difference between `prisma migrate dev` and `prisma db push`? When would you use each? When should you never use `db push`?
